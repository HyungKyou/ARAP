## Domain facts that aren't obvious from a first read of the sample files

These were found by directly inspecting the two xlsx files and diverge from naive assumptions — worth knowing before touching ingestion or calculation code (full detail in PRD §4.1):

- **Neither file has an exchange-rate column.** The per-line booking rate must be *derived* as `원화금액 ÷ 외화금액` (LC ÷ TC) for every row. There is no independent value to validate it against — only a sanity check against the day's spot rate (±30% band).
- **AP's posting date is stored under a column literally named `회계연도` ("fiscal year")**, not under any column called `전기일`. This looks like a mislabeled field from the SAP export, not something to "fix" — map it as the posting date anyway.
- **Currencies present are USD / EUR / JPY / CNY** (the original PRD draft assumed only USD/EUR/JPY). Never hardcode a currency list — derive it dynamically from whatever is in the ledger.
- **AP's G/L accounts mix trade payables with financing debt**: `외상매입금(외화)` / `미지급금(외화)` (payables) alongside `외화단기차입금` (FX short-term borrowings, ~1/3 of AP rows). Whether borrowings belong in the AP exposure is an open policy question (PRD §11); v1 default is to include them.
- **AR has a `네고여부` (Y/N) flag** — receivables already discounted/sold to a bank. v1 default is to include these lines but flag them, not exclude them.
- **AP has a `반제일` (clearing date) column** — a non-empty value means the line is already settled and must be excluded from open-item aggregation. In the current sample, all 300 AP rows are open (반제일 empty), so this exclusion path has no real coverage from the sample data alone — test it with synthetic rows.
- Dates are formatted `YYYY.MM.DD` (dot-separated), not ISO `YYYY-MM-DD`.
- JPY amounts are booked in whole-yen units (원/1엔), not per-100-yen — don't apply a ×100 conversion anywhere.

## Calculation logic (PRD §6) — where subtle bugs are most likely

- **§6.1 has a documented historical defect (fixed in v1.1).** Converting every currency's line by dividing its KRW amount by the day's USD/KRW spot rate collapses the weighted-average booking rate (§6.2) to a constant equal to the USD/KRW rate *for every currency*, making the metric meaningless. The correct approach cross-converts through each currency's own spot rate: for non-USD lines, `외화금액 × (해당통화/KRW 스팟) ÷ (USD/KRW 스팟)`; USD lines pass through unchanged. When touching this code, verify the weighted-average booking rate actually differs across currencies — if every currency produces the same rate, the defect has been reintroduced.
- **§6.3 realized-vs-unrealized split**: 만기일 ≤ 당월 말 → 환차손익 (realized), 만기일 > 당월 말 → 환산손익 (unrealized). Flags/exclusions established in §4.1.3 (settled AP via 반제일, overdue lines, nego lines) must propagate consistently into every downstream feature (F1/F2/F4) — a line excluded upstream must never silently reappear in an aggregate.
- **§6.4** unifies all multi-currency exposure into a single USD/KRW proxy. This is a known approximation (it ignores each currency's own cross-rate volatility) and any report output must carry a disclosure note about it — don't drop that when reworking UI in stage 3.
